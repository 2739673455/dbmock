# dbmock

## 环境要求

### 拉取 Git LFS 数据文件

`data/` 中的数据文件通过 Git LFS 管理。首次使用本仓库前，请先安装 Git LFS，然后在 dbmock 仓库根目录执行：

```bash
git lfs install
git lfs pull
```

`git lfs install` 通常只需为当前用户执行一次。未正确拉取时，数据文件的内容会是以 `version https://git-lfs.github.com/spec/v1` 开头的 Git LFS 指针；执行 `git lfs pull` 后会替换为实际数据。

### 启动依赖服务

本项目需要可访问的 Apache Doris 服务。使用已有服务时，直接在 `.env` 中填写连接信息。

在 dbmock 仓库根目录安装依赖并创建本地配置（作为子模块使用时先进入 `dbmock/`）：

```bash
cp .env.example .env
uv sync
```

`.env` 保存 Doris 连接信息：

```dotenv
DB_HOST="127.0.0.1"
DB_PORT=9030
DB_HTTP_PORT=8040
DB_USER="atguigu"
DB_PASSWORD="123123"
DB_NAME="ecommerce"
```

## 快速开始

### 1. 初始化 Doris

```bash
uv run scripts/init_db.py
```

该命令会删除并重建 `.env` 中 `DB_NAME` 指定的数据库，然后执行全部业务表和内部管理表 DDL。

### 2. 首次生成

在 `src/settings.py` 的 `GENERATION_CONFIG` 中配置规模，然后指定起止月份：

```bash
uv run main.py --start-month 2026-01 --end-month 2026-08
```

### 3. 追加或补充当月

```bash
uv run main.py --end-month 2026-09
```

追加时不要再次初始化数据库。需要小规模验证时，在首次生成命令后加 `--smoke`，日期范围不变，规模缩放到 5%。

本地进度保存在 `.generation-status.json`，包含起始月份、最新已提交截止时间 `cutoff`、已完成月份、当前月份、smoke 模式和待恢复标记 `needs_recovery`。生成进度提交及回滚时自动更新；时间使用北京时间。若运行中断且 `needs_recovery` 为 `true`，需再次执行生成命令完成恢复。该文件仅供查看，追加以数据库记录为准，不要通过修改它调整进度；初始化数据库会删除旧文件。

## 数仓模型

项目在 Doris 中创建 45 张业务表，覆盖以下主题域：

- 公共维度：日期、渠道、页面、行政区划、支付方式和物流公司
- 用户域：用户拉链维度、用户标签及标签关系
- 商品域：SPU、SKU、品牌、类目、商家、店铺和价格变更
- 营销域：促销规则、优惠券模板、适用范围和用户券生命周期
- 流量域：会话、页面访问、搜索和搜索点击
- 互动域：收藏、取消收藏及购物车增删改清
- 交易域：订单明细、订单状态、活动优惠和优惠券分摊
- 支付域：支付明细、订单分摊及支付状态
- 履约域：配送单、配送商品和配送状态
- 售后域：退款、退款状态、退款支付和评价
- 库存域：库存变更流水和 SKU 日末库存快照

表名遵循以下约定：

- `dim_*_zip`：SCD2 拉链维度
- `dim_*`：普通维度或版本维度
- `bridge_*`：多对多关系桥接表
- `dwd_*_di`：明细事件事实表
- `dwd_*_df`：全量日快照表

完整 DDL 位于 `scripts/sql/ecommerce.sql`

## 按月生成与追加

生成器按月保存计划与进度，支持当月补充和跨月追加。已有旧版一次性生成的数据不支持直接追加，首次使用新流程需要初始化数据库。

### 指定月份范围

月份使用 `YYYY-MM` 格式。首次生成指定起止月份，包含首尾两个月；后续追加只传截止月份，起点根据已有进度自动确定。使用以下命令：

```bash
# 首次生成 2026 年 1 月至 8 月
uv run main.py --start-month 2026-01 --end-month 2026-08

# 追加 2026 年 9 月
uv run main.py --end-month 2026-09
```

开始月份不能晚于结束月份，结束月份不能超过当前月份。时间统一使用 `Asia/Shanghai`，每次任务启动时固定本次截止时刻：历史月份生成完整月份，当月只生成到任务启动时的日期和时刻，不生成未来业务数据。

smoke 使用完全相同的月份范围、截止时刻、追加与回滚规则，只将正常规模抽样结果缩放到 **5%**，不再限制为七天：

```bash
# 首次以 smoke 规模生成，仍覆盖完整的 1—8 月
uv run main.py --start-month 2026-01 --end-month 2026-08 --smoke

# 后续自动沿用该数据集的 smoke 模式
uv run main.py --end-month 2026-09

# 按已保存的配置和进度校验，不重新生成
uv run main.py --validate-only
```

缩放在正常规模抽样、取整后执行，再四舍五入；原数量大于零的规模项至少保留 1 个，原数量为零则仍为零。公共地域、类目等种子字典保持完整，SKU 数量随选中 SPU 的关联关系确定，因此总表行数不保证恰好为正常模式的 5%。批次大小和线程数不缩放。同一数据集固定生成模式，不能在正常模式与 smoke 之间切换。

首次生成需要空库，必须提供 `--start-month` 和 `--end-month`。已有生成进度时只提供 `--end-month`，不再接受 `--start-month`；从未完成月份的截止时刻继续，或从最后一个完整月份的下个月月初开始。后续追加保留已有数据，不再执行数据库初始化命令。

### 月份进度与当月补充

系统持久化已完成月份、未完成月份的截止时刻及业务状态。已完整生成的月份禁止重复生成，后续范围必须连续衔接，不能重叠已完成月份或跳过中间月份。

当月属于尚未完成的月份，可以重复将该月作为 `--end-month`，将数据从上次截止时刻补充到本次截止时刻。补充包括截止当天剩余的业务，不能直接从第二天开始；已经生成的业务不能重复写入。指定更晚的截止月份时，自动依次生成中间所有月份。

| 已有进度               | 请求                   | 处理方式                                        |
| ---------------------- | ---------------------- | ----------------------------------------------- |
| 8 月已完整生成         | 再次生成 8 月          | 拒绝重复生成                                    |
| 9 月生成到 22 日某时刻 | 25 日再次生成 9 月     | 补充到 25 日任务启动时刻                        |
| 9 月生成到 22 日某时刻 | 进入 10 月后追加 10 月 | 先补完 9 月，再生成 10 月截至任务启动时刻的数据 |
| 仅完整生成到 8 月      | 指定截止月份为 10 月   | 自动从 9 月开始，连续生成到 10 月的允许截止时刻 |

补充历史未完成月份时，必须先将其生成到月末并标记完成，再推进后续月份。不同进程执行的追加任务也必须延续已有业务状态。

如果本次截止时刻没有晚于已有进度，提示没有新增数据，不执行写入。同一数据库只允许一个生成任务运行，另一个任务必须拒绝启动。

生成进度、各月配置快照、业务状态和回滚所需的月初状态保存在 Doris 内部管理表中，不依赖执行机器上的临时文件。更换机器后仍可继续追加；初始化数据库时一并清除这些管理数据。内部管理表不计入 45 张业务表。 月度暂存保留月初维度、本月变更记录和月末业务状态，不重复保存月初业务状态或整份月末维度；月末维度由月初维度与本月变更重建，在月份完整提交时保存为检查点。

### 跨月业务连续性

跨月订单继续推进支付、配送、退款和评价等后续事件。例如，1 月下单、2 月支付的订单，在追加 2 月时产生支付事件，而不是重新生成订单。

库存、在途与预占数量、购物车、收藏、用户累计消费、积分和用户等级等状态持续继承。日期维度和营销规则随生成范围扩展；已生成的商品价格、用户历史版本和业务标识不能因为结束月份变化而重新计算。

相同起点、逐月配置和种子数据下，一次生成多个月与分次连续追加，最终业务数据应一致；运行时间和装载批次等审计信息可以不同。当月分次补充也遵循这一原则。随机数种子固定为程序中的常量 `42`，不提供配置项或命令行参数。用户等级、活跃状态和标签在月末按累计业务更新；当月部分生成时，对这些字段的校验以最近一次月末评估为准。

当月补充时，订单、支付等事件只新增尚未生成的部分；库存日快照更新原截止日期及本次新增日期，使当天快照反映最新截止时刻的库存。原截止日期之前已经完整生成的日快照保持不变。跨月后补完旧月时，同样需要补齐旧截止日期剩余时间的快照。

### 新用户与新商品

初始用户和初始商品在起始月份月初可用，只投放一次。每个月（包含起始月份）持续生成新注册用户，当月新增用户按注册时间逐步出现，已有用户继续参与业务。初始用户规模和每月新增用户规模分别配置，每月新增用户数必须大于零。

新商品从种子商品池中逐步上架。首次只投放一部分商品，为后续月份保留未上架商品；初始投放规模和每月上新规模分别配置。上新以 SPU 及其关联 SKU 为单位，实际数量受剩余种子商品数量限制。

每月上新包含起始月份，与初始投放分开计算。当月只写入截止时刻前已注册的用户和已上架的商品，不能提前写入未来注册或上架的记录。

种子商品池耗尽后停止新增商品，已有商品继续交易，并在日志中提示种子已耗尽。不能重复使用同一商品充当新商品，也不凭空生成种子之外的商品。追加时，新用户增长不受商品池耗尽影响。

商品采用按 SPU 分批上架、关联 SKU 同时上架、按月固定计划的方式：

1. 首次按种子文件中的固定顺序选取初始 SPU，将其全部关联 SKU 在起始月份月初上架。
2. 每个月从尚未安排上架的 SPU 中，按同一固定顺序选取当月配置的上新数量；不足时取剩余全部商品。
3. 在写入当月业务数据前，将选中的 SPU、关联 SKU 及具体上架时间保存在 Doris 的月度计划中。同一 SPU 的所有 SKU 使用相同的上架时间，后续补充和失败重试沿用原计划。
4. 生成进度到达计划上架时间时，才写入 SPU、SKU 维度，并生成各 SKU 的初始库存及入库流水。后续浏览和交易只使用当时已经上架的商品，已有商品继续参与业务。

商品是否已经使用，由商品维度和月度计划共同确定：

| 记录情况                             | 状态             | 后续处理                     |
| ------------------------------------ | ---------------- | ---------------------------- |
| 商品维度中已有记录                   | 已上架           | 继续交易，不再占用新品名额   |
| 月度计划中已有安排，商品维度尚无记录 | 已安排、等待上架 | 按原计划到时上架，不重复选择 |
| 商品维度和月度计划中均无记录         | 尚未安排         | 可供后续月份选择上新         |

不为每个 SKU 单独维护“是否使用”标记，也不按是否产生订单判断商品是否已上架。SPU 管理上新名额，SKU 管理各自的价格、库存和交易；已上架商品即使后来下架，也不重新进入新品池。

失败月份回滚时，删除该月新增的商品维度和初始库存等业务记录，但保留月度上架计划。重试仍按原时间上架同一批商品，不能重新选择其他商品。

### 月度生成规模

所有数据规模统一在 `src/settings.py` 的 `GENERATION_CONFIG` 中配置；数据库连接信息仍使用 `.env`。配置保留固定基准值，作为正态分布的均值，实际规模通过抽样确定。默认基准值如下：

| 配置项               | 默认基准值 | 含义                                 |
| -------------------- | ---------: | ------------------------------------ |
| 初始用户数           |      6,000 | 起始月份月初已有用户                 |
| 每月新增用户数       |      1,000 | 每个完整月份的新注册用户             |
| 初始商品 SPU 数      |      1,000 | 起始月份月初投放，包含关联 SKU       |
| 每月新增商品 SPU 数  |        150 | 从剩余种子商品中上架，包含关联 SKU   |
| 每月订单明细基准量   |      5,000 | 订单行数，不是订单数                 |
| 每月页面访问基准量   |    200,000 | 页面访问事件数                       |
| 每月搜索基准量       |     30,000 | 搜索事件数                           |
| 每月新增促销规则数   |          2 | 新建促销规则，已有未结束活动继续有效 |
| 每月新增优惠券模板数 |          4 | 新建模板，已有优惠券继续其生命周期   |
| 初始仓库数           |         12 | 首次创建，后续沿用                   |

SKU 数随选中的 SPU 及其种子数据确定，不单独配置。商品不足时仅使用剩余商品，不重复投放。初始用户、初始商品和初始仓库配置只在首次初始化时生效，后续修改不补建或删除这些初始对象。

规模抽样遵循以下规则：

- 均值为配置的基准值，标准差为基准值乘以波动比例。默认波动比例为 `15%`，在`GENERATION_CONFIG` 中统一设置，并允许各规模项单独覆盖；比例为 `0` 时直接使用基准值。
- 使用截断正态分布，在均值上下 3 个标准差内抽样，超出范围则重新抽取，最后四舍五入为整数。基准值和波动比例不能为负数。
- 必须为正的数量至少为 1，包括每月新增用户数；允许为零的规模项取整后不得小于 0，基准值为 0 时固定为 0。
- 初始用户、商品和仓库规模只在首次生成时抽取一次；月度规模每个月分别抽取一次。当月抽取的是整月目标，只执行截止时刻前的部分。
- 抽样使用程序固定随机种子，结合月份和配置项名称确定各自的随机序列，避免其他配置项或执行顺序影响结果。
- 月度计划持久化各项基准值、波动比例和实际抽样结果（smoke 保存缩放后的实际规模）；当月补充、跨月补完和失败重试都沿用原结果，不重新抽样。新月份读取最新配置后重新抽取。
- 抽样结果仍需校验订单、访问和搜索等数量之间的业务约束；无法支撑生成的配置在写入业务数据前拒绝。商品投放量另外受剩余种子数量限制，计划同时记录抽样数量和受限后的实际投放数量。
- 批次大小、线程数等运行参数保持固定，不参与规模抽样。

例如，每月新增用户基准值为 `1,000`、波动比例为 `15%` 时，标准差为 `150`，实际数量通常围绕 1,000 波动。促销规则等基准值较小的整数取整后变化较小，可单独设置更高的波动比例。

订单明细、页面访问和搜索等由整个区间的固定总量改为月度基准量，再结合周末、促销和增长因素安排月度计划与日内分布。规模由 `GENERATION_CONFIG` 控制，不额外叠加月度总量增长；可通过调整新月份的基准值控制增长。周末和促销权重调整月内分布。

完整月份执行完整计划；当月只生成截止时刻前的部分，不能将整月的数据量压缩到已经过去的几天。后续补充使用同一份月度计划，不因执行次数或截止时刻变化而重新分配已生成的数据。

### 月度配置与种子数据

每个新月份开始生成前读取生成配置，完成规模抽样和业务约束校验，并持久化该月配置快照及实际抽样结果；生成后保留这些记录。先保存再写入业务数据，确保中途失败后也能确定该月使用的配置和规模。

同一月份后续补充、跨月后补完旧月，以及失败回滚后的重新生成，都使用该月已保存的配置，不采用`GENERATION_CONFIG` 中的新值。只有开始一个尚未建立配置快照的新月份时，才使用新的生成配置。程序启动时加载代码中的配置，同一次任务连续生成多个月时，按月复制和冻结该配置。修改 `settings.py` 后需重新运行命令，修改才会生效。

例如，9 月生成到 22 日后修改每月新增用户数，继续补充 9 月时仍使用旧值；首次开始生成 10 月时使用新值。跨月订单和优惠券等已生成业务继续原有计划，不因新月份配置变化而重新安排。

首次生成记录全部输入种子文件的文件清单及内容摘要，包含商品、类目、品牌、店铺、行政区划、支付方式、物流公司和来源信息等实际读取的种子数据。后续每次生成前，以及同一任务进入新月份前，都校验种子是否一致；文件新增、缺失或内容变化时拒绝生成，并列出变更文件。生成期间不得修改种子文件。

质量报告等生成产物不参与种子校验，生成配置的修改按月度配置规则处理。需要更换种子数据时，应初始化新的数据集，不能继续追加到原数据集。

### 月度质量校验

每个月生成后立即校验，通过后才提交该月生成进度，再进入下个月。当月部分生成也需要校验，通过后保存实际截止时刻，不标记整月完成。

校验依据各月冻结的生成配置和实际截止时刻计算预期数量，检查跨表关联、时间顺序和状态一致性。允许合理的待支付、待履约等中间状态，以及尚未到达计划发生时间或样本不足导致的空表；应当已经发生的业务缺失仍视为失败。

质量报告只在校验失败时生成；校验成功时不生成报告，并清理旧报告。不再执行真实性指标的比例或分布阈值检查。库存数量、变动守恒和缺货取消证据等正确性检查仍保留。

### 失败时整月回滚

生成或质量校验失败时，回滚失败月份，保留此前已完成的月份。回滚不仅删除当月事实数据，还需要恢复月初状态：

- 删除失败月份写入的订单、流量、支付、履约、退款、库存流水和库存快照等数据。
- 删除该月新增的用户、商品维度和营销规则等记录。
- 恢复被更新的用户历史版本、标签关系及其他跨月维度状态。
- 恢复月初的库存、购物车、收藏、用户累计指标，以及待支付、待履约、待退款等业务状态。
- 将生成进度退回上个月末，下次从失败月份月初重新生成；首次生成的月份失败时，恢复到首次生成前的状态。

回滚保留失败月份已经冻结的配置和种子摘要，重试仍使用原计划。首次生成月份失败时，清空其业务写入，保留起始月份及重试所需的管理信息。

例如，9 月已生成到 22 日，在 25 日补充时失败，9 月已有的部分数据也一并回滚，下次重新生成整个 9 月。回滚不能删除 8 月创建、原本计划在 9 月继续处理的订单，只撤销其 9 月新增事件和状态变化。

任务中断后也必须识别未完成的写入，先完成失败月份的回滚，再允许重新生成。回滚前先确认数据库没有尚未结束的装载事务，避免延迟提交与删除冲突；等待超时则保留待恢复状态，之后重新运行生成命令。回滚尚未完成时不能继续追加。参数、配置、种子校验或并发检查在业务写入前被拒绝时，不回滚已有正常数据。

## 验证

离线回归测试不连接数据库：

```bash
uv run python -m unittest discover -s tests -v
```

真实 Doris 集成测试默认跳过。指定专用测试实例后启用；测试会新建随机命名的测试数据库，并在结束后删除，不使用 `.env` 的业务库：

```bash
DBMOCK_TEST_DORIS=1 DBMOCK_TEST_HOST=127.0.0.1 \
DBMOCK_TEST_PORT=19030 DBMOCK_TEST_HTTP_PORT=18040 \
uv run python -m unittest discover -s tests -p test_doris_integration.py -v
```

测试账号默认 `root`、空密码，可通过 `DBMOCK_TEST_USER` 和 `DBMOCK_TEST_PASSWORD` 覆盖。账号需要创建、删除测试数据库和读取会话状态的权限。
